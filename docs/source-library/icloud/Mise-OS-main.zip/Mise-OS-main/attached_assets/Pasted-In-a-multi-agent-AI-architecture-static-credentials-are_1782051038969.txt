In a multi-agent AI architecture, static credentials are a massive security risk. If an agent like *Omar Reviewer* or *Schema Sora* holds a static, long-lived API key in its memory, a clever prompt injection attack could trick the agent into exfiltrating that key, compromising the entire tenant's infrastructure.
Within the **Mise Orchestra**, HashiCorp Vault acts as **The Wine Cellar (Vault Hana, Role 21)**. It ensures that agents never hold permanent keys. Instead, they are handed **ephemeral, just-in-time (JIT) tokens** that expire the moment the "dish" is cooked.
Here is the architectural breakdown of how HashiCorp Vault securely hands ephemeral tokens to the Mise Orchestra agents using **AppRole Authentication** and **Dynamic Secret Engines**.
### The Core Mechanisms of the Vault
To make this work in a multi-tenant SaaS, we rely on three HashiCorp Vault features:
 1. **AppRole Auth Method:** The standard way machines (agents) prove their identity to Vault.
 2. **Dynamic Secrets Engines:** Vault plugins that generate *brand new*, temporary credentials on the fly (e.g., a new AWS IAM role, a new Postgres user, or an ephemeral GitHub token).
 3. **Leases & TTLs (Time-To-Live):** Every secret has an expiration timer attached to it.
### The Step-by-Step Security Flow
Let’s trace a real scenario: **Tenant A** merges a PR. The mise.yaml blueprint summons **Schema Sora (Role 19)** to run a database migration on Tenant A's production PostgreSQL database.
#### Step 1: The AppRole Handshake (Identity Bootstrapping)
When the orchestration engine spins up the isolated container for *Schema Sora*, it does not give Sora the database password. Instead, it gives the container two pieces of identity:
 * role_id: A non-secret identifier (like a username) specifying that this container is acting as "Schema Sora for Tenant A".
 * secret_id (Wrapped): A single-use, cryptographically wrapped token (like a password).
Sora's initialization script unwraps the secret_id and sends both to Vault. Vault verifies the identity and returns a short-lived VAULT_TOKEN scoped *strictly* to Tenant A's namespace.
#### Step 2: Requesting the Ephemeral Credential (The Checkout)
Now authenticated, *Schema Sora* needs to access the database. She makes an API call to Vault's Database Secrets Engine:
```bash
# Sora requests a database credential with a 15-minute lifespan
curl -H "X-Vault-Token: $VAULT_TOKEN" \
     -X GET https://vault.mise-orchestra.internal/v1/tenant-a/database/creds/migration-role

```
#### Step 3: Vault Generates the Dynamic Secret
Vault intercepts this request, connects to Tenant A's PostgreSQL database using its own master credentials, and dynamically executes:
```sql
CREATE ROLE "v-sora-tenantA-x7k2mQ" WITH LOGIN PASSWORD 'A1b2-C3d4-E5f6-G7h8' VALID UNTIL '2026-06-21 07:20:00';
GRANT ALL PRIVILEGES ON SCHEMA public TO "v-sora-tenantA-x7k2mQ";

```
Vault returns this unique, randomly generated username and password back to Sora.
#### Step 4: Execution & Automatic Revocation (The Clean Up)
Sora runs the database migration using the temporary credentials.
 * **If she finishes early:** She tells Vault to explicitly revoke the lease. Vault immediately drops the user from the database.
 * **If the container crashes or Sora goes rogue:** The 15-minute TTL expires naturally. Vault's internal clock triggers a cleanup routine and drops the user from the database automatically. The credentials become useless dust.
### The "Sidecar" Defense: Keeping Tokens Out of the LLM
Even with 15-minute ephemeral tokens, feeding a raw database password directly into an LLM's context window is risky (a hallucination could cause it to print the password into the runtime.execution_logs).
To achieve **Zero-Trust Agentic Security**, Mise Orchestra utilizes the **Sidecar Proxy Pattern**:
 1. **The LLM is isolated:** The AI model running *Schema Sora* has no network access to the outside world and holds NO secrets.
 2. **Tool-Calling Abstraction:** When the LLM decides it needs to run a SQL command, it outputs a JSON tool-call:
   {"tool": "execute_sql", "query": "ALTER TABLE users ADD COLUMN age INT;"}
 3. **The Sidecar Intercepts:** A secure sidecar container (written in Go or Rust) sitting next to the LLM intercepts this request.
 4. **The Sidecar Fetches the Secret:** The sidecar (which holds the Vault AppRole) asks Vault for the ephemeral database token.
 5. **The Sidecar Executes:** The sidecar connects to the database, runs the SQL query, drops the credential, and simply returns the Success: Table altered string back to the LLM.
**The Result:** The AI agent *directs* the infrastructure, but the AI agent never actually *touches* the radioactive keys.
### Connecting it to the PostgreSQL Schema
In the schema we built previously, this maps directly to the tenant_auth.workspace_secrets table:
```sql
-- The backend knows exactly which Vault path to give to the Agent Sidecar
SELECT vault_reference_path 
FROM tenant_auth.workspace_secrets 
WHERE workspace_id = 'tenant-a-uuid' 
AND secret_name = 'DB_MIGRATION_ROLE';

-- Returns: "tenant-a/database/creds/migration-role"

```
Because Vault integrates with Kubernetes, AWS IAM, GitHub Apps, and Databases, **Vault Hana (Role 21)** can vend ephemeral AWS assumed roles for deploying infrastructure, ephemeral GitHub installation tokens for pushing code, and ephemeral DB credentials for migrations—all governed by the precise Character Capabilities we defined in the sys_core schema.
